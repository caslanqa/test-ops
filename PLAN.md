# TestOps — Development Plan (post-Phase 1)

**Status:** The Phase 1 core works end to end and has been verified (see repo memory / previous conversation summary). This document collects in one place the **remaining work**, organized by the phases in design-doc.md, and the **known gaps** found in the code review.

## 0. Priority technical debt (independent of phases, to be addressed first)

- [ ] **The audit log is never written.** The `AuditLog` Prisma model exists, but no service ever inserts into it. Design-doc section 8: "Critical user actions must be written to the audit log" — currently not met. Suggestion: record an entry for critical actions such as write/delete/role change via `AccessControlService` or a separate `AuditService`.
- [x] **Rate limiting is not actually enforced.** _(2 October 2026: `@nestjs/throttler` 6 + `common/rate-limit.ts` `AppThrottlerGuard`. The general limit is 600 per minute per user/anonymous IP (a single counter for the whole API, not per route); sign-in/registration/password change additionally get 10 per account+IP and 60 per IP. On 429: the standard `Retry-After` header and the `Too many attempts. Try again in N seconds.` message; `X-RateLimit-Limit/-Remaining/-Reset` headers; `/health` and `/ready` are exempt from the limit. `RATE_LIMIT_PER_MINUTE`, `AUTH_RATE_LIMIT_PER_MINUTE`, `AUTH_IP_RATE_LIMIT_PER_MINUTE` (0 = off) and `TRUST_PROXY` for a reverse proxy. The sign-in screen shows the 429 message. `tests/smoke/ratelimit.mjs` runs in CI. Remaining: counters are kept in memory (multiple replicas need Redis storage); no account lockout against distributed attempts on a single account from different IPs; no `RateLimit-Policy` header, the `X-RateLimit-*` equivalent is used instead. 10 October 2026: requests that failed to authenticate were not limited at all, because AuthGuard rejects them before the throttler runs, and every guessed API token cost a database lookup. They now count per client address against the general limit (`AuthFailureLimiter`); an address over it gets 429 and no API token lookups, while valid web sessions from that address keep working. `tests/smoke/ratelimit.mjs` covers it.)_ We document the FR-077 header format, but there is no guard such as `@nestjs/throttler`; a client can send as many requests as it wants.
- [ ] **No automated tests.** There are no tests on either the API side (Jest/e2e) or the web side (component/e2e). At a minimum, smoke-level e2e tests should be added for auth + access control + the run/result flow.
- [ ] **The backup/restore procedure is not written down.** _(2 October 2026: the backup commands are in the README (`pg_dump`, `docker compose cp`); the restore steps have not been written or tested yet.)_ Design-doc section 8 and MVP acceptance criterion 7: the backup/restore steps for PostgreSQL + the attachment volume are not documented.
- [x] **No graceful shutdown.** Node ran as PID 1 without a SIGTERM handler: `docker stop` waited 10 seconds and killed it, cutting off running uploads and CI submissions and leaving half-written files in the attachments temp directory. _(10 October 2026: `main.ts` handles SIGTERM/SIGINT itself: the server stops taking connections and lets running requests finish, idle keep-alive connections close at once, then the modules shut down (database) and the process exits, also as PID 1. Compose runs the app with `init: true` and a 30-second `stop_grace_period`. Checked by stopping the process during a slow 3 MB upload: before, the upload broke and a temp file stayed behind; after, the upload is stored and the process exits right after it. Not yet checked in a container.)_
- [ ] **FR-017 (auto-case-creation from automation results) is not in the backend yet.** Currently `results.service.ts` simply returns 404 when a result does not match an existing `testCaseId`; there is no fallback matching by name/suite and no automatic case creation.

### 0.1 Code review findings (2 October 2026)

**Security**

- [x] **No cross-project/cross-workspace ID validation (FR-003, section 8).** _(2 October 2026: scope checks added to `AccessControlService`; all of the points below were fixed and verified with a 34-scenario smoke test against the running stack.)_ Foreign keys in the request body are not checked to belong to the project in the URL:
  - `defects.service.ts` create/linkResults `resultIds`: another project's result can be linked and then read via `getOne`, including `caseSnapshot`.
  - `requirements.service.ts` linkCases, `plans.service.ts` create/addCases `testCaseIds`: another project's case can be linked and its full content read.
  - `unlinkCase` / `removeCase` / `unlinkResult`: the parent record is not checked to belong to the project → links in another project can be deleted.
  - `suiteId`, `parentId`, `milestoneId`, `assigneeId` are not validated; there is no cycle check for suite `parentId` (moving a suite into its own child suite).
  - `workspaces.service.ts` / `projects.service.ts` `updateMemberRole` / `removeMember`: `memberId` is not checked to belong to the workspace/project in the URL → anyone who is an admin in their own workspace can make their membership in another workspace ADMIN or remove members (**privilege escalation**).
- [x] **Default JWT secret.** _(2 October 2026: `config/jwt-secret.ts` stops bootstrap in production when the secret is empty, the example value or shorter than 32 characters; compose rejects an empty value via `${JWT_SECRET:?}`; `scripts/ensure-env.sh` generates a random secret; `start.sh` shows the logs and exits with an error if the app does not become ready, and the bug where it exited silently when `APP_PORT` was missing from `.env` was fixed.)_ `configuration.ts` and `docker-compose.yml` use `change-me-in-production`; because `start.sh` copies `.env.example`, JWTs can be forged on a default installation. It should refuse to start in production with a default/empty secret.
- [x] **A leaked API token could keep its access.** An API token could create new API tokens, so revoking a leaked token didn't end the access; tokens never expired; and a password change left existing sessions valid for up to 8 hours. _(10 October 2026: API tokens are created, listed and revoked only from a signed-in web session (403 for an API token). Workspace and project member management (invitations, adding project members, role changes) is closed to API tokens too, through a `@WebSessionOnly()` decorator enforced in `AuthGuard` that replaced the per-service check. A token gets a lifetime of 1–365 days (`expiresInDays`); when omitted it defaults to 90 days, and an explicit `null` means no expiration (the Account page sends it for "No expiration"). Expired tokens get 401. A password change signs out every other session through `users.sessionVersion`, carried in the JWT as `sv`, and returns a new session token to the browser that made the change; sessions from before the upgrade stay valid. The password change also revokes all of the user's API tokens in the same transaction, and is conditional on the session version, so concurrent changes get 409. `tests/smoke/users.mjs` covers it, including an expired token (set through the database). Remaining: per-token permissions (design-doc section 3). Legacy tokens created before this change have no expiry and never expire until revoked.)_
- [x] **Postgres is exposed to the host.** _(2 October 2026: the port is bound only to `127.0.0.1`; `prisma migrate dev` from the host keeps working. The default DB password still comes from `.env` — it is not generated automatically because of the risk of a mismatch with an existing volume.)_ `docker-compose.yml` exposes 5432 externally with the default password; it should be closed by default (with an override file if needed).

**Correctness / functional**

- [ ] **FR-072 is missing.** No list endpoint has pagination/sorting.
- [x] **Coverage bug.** `requirements.service.ts` `take: 200` truncates the results of all linked cases together; with frequently run cases, the latest status of the other cases is lost. Also N+1 queries per requirement. _(10 October 2026: measured before the fix, a requirement whose failing case sat next to a case with 220 newer results was reported as passing only, and its other cases showed as untested. Coverage now reads the latest attempt of each linked case across the project's runs in one `DISTINCT ON` query, so no case can push another out of the report, and the per-requirement queries are gone: 200 requirements over 40,000 results went from ~1.95 s to ~75 ms. `tests/smoke/api-crud.mjs` covers it.)_
- [x] **Bulk submit is not atomic.** `results.service.ts` `bulkSubmit` is sequential and has no transaction; a single bad item returns 404 but the earlier results stay written, and the client cannot tell which ones were saved. _(10 October 2026: an upload is one transaction and every case is checked before anything is written, so one bad item rejects the whole upload and nothing is saved; a single result goes through the same path. `tests/smoke/results.mjs` covers it.)_
- [x] **Idempotency race.** The `externalTestId` check is outside the transaction; concurrent CI jobs can create duplicate records. If an old attempt's `externalTestId` comes in, `RunCase.status` is reverted to the old result. _(10 October 2026: measured before the fix, 10 parallel submits for one case left 10 "latest" rows and duplicate attempt numbers, 10 parallel re-sends of one key stored it 10 times, and parallel first results for a case not yet in the run returned 500. Result writes now hold a transaction-level advisory lock per run case, taken in sorted order so parallel uploads can't deadlock, and keep the run `FOR SHARE`, so completing a run waits for results being written. `results` has unique `(runCaseId, attemptNumber)` and `(runCaseId, externalTestId)`. A new attempt continues after the highest number (deleting attempt 2 of 3 used to give the next one number 3 again). Re-sending an older attempt's key updates only that attempt and no longer rolls back `RunCase.status`. Migration `20261010200000_result_attempt_integrity` repairs existing duplicates without deleting any result. `tests/smoke/results.mjs` fails on the old code and passes now.)_
- [x] **Bulk uploads were capped at 100 KB of JSON.** Express's default body limit rejected 500 results with ~1 KB failure messages, or a single result with a long log, with 413, although the API documents 500 results per upload. _(10 October 2026: `JSON_MAX_REQUEST_SIZE_BYTES`, 10 MiB by default, applies to the bulk result upload only; every other JSON request, including unauthenticated sign-in and sign-up, keeps the 100 KB default so nothing large is buffered before throttling. Both are stated in the OpenAPI description; `tests/smoke/results.mjs` uploads 500 such results (~550 KB) in CI.)_
- [x] **Unbounded result payloads.** `comment` and `stepResults` had no size limits, so one 10 MiB request could fan out into many rows. _(A result `comment` is limited to 10,000 characters, `stepResults` to 200 items with comments of 2,000 characters; larger values return 400. Stated in the OpenAPI description and README; `tests/smoke/results.mjs` covers it.)_
- [x] **Delete/unlink returns 500.** Prisma `delete` throws P2025 when the record does not exist, and there is no global exception filter → 500 instead of 404. _(Unlink operations were changed to `deleteMany` + 404, and the other deletes check for existence first. There is still no general Prisma exception filter.)_ _(10 October 2026: `common/prisma-exception.filter.ts` answers database errors caused by the request with 4xx: a unique value taken by a parallel request 409, a record deleted in the meantime 404, a missing or still-used reference 409, numbers out of range and NUL characters 400; anything else stays 500 and is logged. The DTOs reject empty IDs, numbers outside the integer range and negative durations, and `PATCH /workspaces/:id` validates its body. `tests/smoke/api-crud.mjs` covers it.)_
- [x] **An archived project stays writable and can't be restored.** `DELETE /projects/:id` only set `archivedAt`, which hides the project from the lists; the access checks ignored it, so cases, runs and results could still be added, and nothing could undo the archiving. _(10 October 2026: an archived project is read-only: its data can be read, and every change gets 409, also results from CI. Admins can still manage its members, turn public run links off and restore it with `POST /projects/:id/restore`; `GET /workspaces/:id/projects?archived=true` lists archived projects. The web app hides editing actions in an archived project and says why. `tests/smoke/api-crud.mjs` covers it. Remaining: the web app has no controls to archive or restore a project.)_
- [x] **Plan → run was incomplete (FR-030).** A run started from a plan didn't take the plan's milestone, environment or configuration, listed the cases in creation order instead of plan order, and copied cases archived since; assignments (`PlanCase.assigneeId`, `RunCase.assigneeId`) were never written, so "a tester runs what is assigned to them" wasn't possible. _(10 October 2026: a run from a plan takes those fields unless the request sets them, keeps the plan order and leaves archived cases out; an ad hoc run keeps the given order and rejects archived cases. Plans assign cases when created, when cases are added or per case (`PATCH /plans/:id/cases/:caseId`), runs take the assignments over for people who still have access, and run cases can be reassigned (`PATCH /runs/:id/cases/:runCaseId`); `GET /runs?assigneeId=` lists someone's runs. In the web app: an assignee when creating a plan, an assignee per case in a run, and "Assigned to me" filters for runs and cases. `tests/smoke/api-crud.mjs` covers it. Remaining: no plan detail page to change single assignments in the web app.)_

## 4. Release — container registry publish

**Reproducible build:** `package.json` `packageManager: pnpm@12.8.1` — Docker (corepack), CI (`pnpm/action-setup`) and local pnpm all use the same version; the version is recorded in the lockfile with its integrity hash.

**Current state (2 October 2026):** No manual steps. On every push/merge to master that changes the image's inputs (`apps/**`, `Dockerfile`, `package.json`, `pnpm-*`; since 3 October 2026), `release.yml` runs CI, computes the version with `scripts/next-version.sh` (the first version comes from `package.json`; after that `feat:` → minor, `type!:` / `BREAKING CHANGE:` → major, everything else → patch), publishes the image to `ghcr.io/caslanqa/testops`, verifies that it can be pulled anonymously, and then creates the `vX.Y.Z` tag + a GitHub Release (automatic notes). Because the tag is created with `GITHUB_TOKEN`, it does not trigger other workflows; the release happens within the same run.

- [x] **The repo is not on git/GitHub yet** — the workflow can never run. _(2 October 2026: `github.com/caslanqa/test-ops`; the first `v0.1.0` is released automatically on the first merge to master.)_
- [x] **No quality gate before publish.** _(`ci.yml` is called as a reusable workflow.)_ The image is published without build/typecheck/test having passed → a separate CI job and `needs:` on publish.
- [x] **linux/amd64 only.** _(QEMU + `linux/amd64,linux/arm64`; index annotations for GHCR.)_ Runs under emulation on Apple Silicon / ARM servers → `setup-qemu-action` + `platforms: linux/amd64,linux/arm64`.
- [x] **An unversioned build becomes `latest`.** _(The raw line was removed; a `{{major}}.{{minor}}` tag was added.)_ `type=raw,value=latest,enable={{is_default_branch}}` makes main `latest` on a manual trigger; since `latest` is already produced for semver tags by `flavor: latest=auto`, this line should be removed.

### 7.4 Paid-plan features: how they work and our design

These features were not observable on the free plan; their behaviour comes from the reference tool's public user documentation, summarised in our own words. Each entry ends with our design, which deliberately stays simpler or goes further where that serves self-hosted teams better.

- [ ] **Test case review.** Works like a pull request for a case: instead of saving, the author sends a new case or a change to reviewers (or the project's default reviewers). Reviewers see a field-by-field diff (steps and parameters included), approve, request changes, edit, merge or decline, and comment. Projects can make review mandatory and set a required number of approvals; editing a review clears earlier approvals; an open change request blocks merging; until merge the current case version stays live and usable in runs. _Our design:_ `CaseReview` (case, base version, proposed snapshot, reviewers, votes, status open/merged/declined) plus a case version counter that invalidates stale votes; project settings `reviewRequired` and `requiredApprovals`; no auto-merge in v1.
- [ ] **Requirement statuses, types and hierarchy.** Requirements form a tree (parent requirement), have a status (e.g. draft, review, rework, valid, implemented, not testable, obsolete), a type (epic, user story, feature) and attachments; lists filter by author, status, type and date. TestOps already has requirements with case links and coverage. _Our design:_ add `parentId`, a configurable status list, type and attachments; keep external tracker sync a separate, optional layer (section 2).
- [ ] **Traceability matrix.** One row per requirement with its external ID, linked cases and defects; expanding a row shows each linked case with its latest result and each defect with its status. Linked/unlinked tabs with totals, filters by requirement status, result status and defect status, a warning when a requirement changed after its cases last ran, CSV/PDF export, and stored snapshots. _Our design:_ a live query (requirement → case → latest result → defects) over our own requirements first, with linked/unlinked tabs and CSV export; snapshots and external requirements later.
- [ ] **Dashboards and widgets.** Any number of dashboards, private or shared with the team, scoped to all or some projects. Widget types: single value with change against a previous period, event counts over time, distribution (donut/bar) by a field, time series, and a table fed by a saved query. Dashboards and widgets can be cloned and shared by public (optionally password-protected) link; viewers only see projects they can access. _Our design:_ a widget is `{type, entity, filters, groupBy, period}` served by one generic aggregate endpoint; four types (value, distribution, time series, table); share by token later.
- [ ] **Query language and saved queries.** Queries pick an entity (case, run, result, defect, plan, requirement) and an expression with comparisons, contains, empty checks, `in`, and/or/not, parentheses, relative-date functions (now minus 7 days, start of day/month), the current user, custom fields, and simple aggregates with group-by/having. Saved queries are live, private or shared, can feed dashboard tables and can be the case source of a new run. _Our design:_ a small expression language compiled to parameterised Prisma/SQL filters over a whitelist of entities and fields (never raw SQL); saved query = name, entity, text, visibility; a run built from a saved query resolves it to case IDs once, at creation time.
- [ ] **Webhooks.** Per project: title, URL, a secret and the subscribed events (cases, suites, plans, runs started/completed/aborted, results, defects created/resolved, milestones, shared steps, custom fields, reviews). The reference tool sends its secret as a plain header, documents no retries and disables a webhook after slow responses or two days of failures. _Our design (stronger):_ an HMAC-SHA256 signature over timestamp + body, retries with exponential backoff, a delivery log visible in the UI, auto-disable after N consecutive failures with a notice, and an envelope of event name, timestamp, actor, project and payload (FR-079, section 2).
- [ ] **Parameterised cases and shared parameters.** A case can have single parameters (combined as a Cartesian product, e.g. 4 browsers × 3 OS = 12) and parameter groups (each row is one valid combination); adding the case to a run creates one instance per combination, capped at 1,024. Each instance has its own result; siblings are listed together and muting one mutes all. Shared parameters are defined at workspace level, assigned to projects, read-only inside cases, and can be turned into local copies when deleted. Run configurations expand the same way. _Our design:_ expand at run creation into run-case instances holding their parameter values, with a hard cap; shared parameters later as a workspace table plus project assignment.
- [ ] **Roles, groups and project access.** Fixed Owner/Administrator/Member roles plus custom roles with create/read/update/delete per entity and a few special permissions (start runs, mute, review); one role can be the default for invited users; deleting a role moves its users to the default. Two independent gates: the role says what a user may do, project access says where. Projects are public (all members) or private (shared with users or groups); groups grant visibility only. API tokens inherit their user's permissions. _Our design:_ role = permission map per entity; `ProjectMember` rows can point at a user or a group; keep our per-project roles as built-in roles and add custom roles on top.
- [ ] **Run execution details.** Statuses passed, failed, blocked, skipped, **invalid** (could not be finished properly, so inconclusive), **retest** (set when a case is run again) plus custom statuses; failed, blocked, invalid and custom negative statuses offer defect creation, skipped records without a dialog. Runs complete manually or automatically when every case has a result, or are aborted; the verdict is passed only if every counted case is positive, **muted cases excluded**, computed once at completion. Time: total = sum of case durations, elapsed = first to last result, estimate = average of earlier durations. Team stats = time and results per person; timeline = one bar per test (duration, status) for automated runs; share report = public read-only link; export CSV/PDF. A guided "wizard" walks through cases one by one. _Our design:_ configurable statuses, abort, the muted-excluded verdict and the timer first; team stats as one grouped query; timeline from result start/end times; our existing share link becomes the report link.
- [ ] **Muted and flaky cases.** A muted case still runs and records results, but negative results don't affect the run verdict; muting in a run mutes the case in the repository; changing it after completion doesn't recompute the verdict. Flaky is a tracking flag only. _Our design:_ as described; muting needs its own permission.
- [ ] **Shared steps.** Project-level or workspace-wide (a project step can be promoted, irreversibly), organised in nested folders that can be cloned. Edits apply immediately to every case that uses the step; there is no versioning. Deleting offers "inline into every case first" or "remove from cases", so no case breaks. _Our design:_ cases store a reference to the shared step and resolve it when read; run snapshots copy the resolved steps; delete inlines by default.
- [ ] **Trash and retention.** Only deleted cases go to the trash; they keep their fields and come back without a suite; suites, runs, plans and defects are deleted immediately. Hosted plans limit how long results, defects and logs are kept. _Our design:_ we already archive and restore cases, plans, projects and requirements; add a trash view; retention, if ever, is an optional per-workspace setting, never a hidden limit.
- [ ] **AI assistants.** Generate manual cases from requirement or issue text, score how ready a case is for automation, turn manual cases into automated tests and export them for common frameworks, run them in a hosted browser cloud; a monthly credit pool; one workspace switch turns everything off, and capabilities can be limited by role. _Our design:_ section 6 (own provider key, workspace switch, human approval); start with "draft cases from a requirement".
- [ ] **SSO and SCIM.** SAML 2.0 with verified company email domains (DNS TXT record), new users get the default role, IdP groups can map to workspaces; SCIM 2.0 provisions users (create, deactivate keeps their data) and groups. _Our design:_ OIDC first through a standard library (most self-hosted teams run Keycloak, Entra ID or Google), mapping IdP groups to our groups; SAML and SCIM later.
